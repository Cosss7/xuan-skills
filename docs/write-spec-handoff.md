## 已确认的 `write-spec` 决定

### 定位

- skill 名称：`write-spec`，不使用 `xuan-` 前缀。
- user-invoked only。
- 放置目录：`skills/xuan/write-spec/`。
- 与现有 `xuan-to-prd` 无关；不要删除、替换、迁移或重新定义 `xuan-to-prd`。
- 默认面向准备建设的新功能或新需求。
- 同时支持：
  - 新功能；
  - 对已有功能提出新增或变更需求；
  - 为完整的已有功能补建 spec。
- 不能把 skill 描述成“从现有代码反向生成 spec”的专用工具。

### 目标产物

- 工作阶段维护决策记录。
- 讨论闭合且用户明确授权后，写一份或多份正式 spec。
- 文档数量和提纲由实际领域边界决定，不使用固定 PRD 模板。
- 对已有实现，spec 区分目标模型、当前实现映射、现状偏差、已有保障和演进验收。
- 对全新功能，不虚构当前实现；改为调查相邻模块、既有约束和可复用能力。
- 正式 spec 描述行为、边界和可验证结果，不默认锁死类名、函数、存储机制或实现步骤。
- 不默认包含任务拆分、负责人、排期或完整讨论历史。

### 假设与调查

- 能从代码、测试和已有文档确认的事实由 Agent 自行调查，不询问用户。
- 会改变规范行为、领域边界或演进方向的假设必须得到用户明确确认。
- 编辑性且不影响语义的决定可以由 Agent 处理。
- 不得把不确定事实写成用户已经确认的决定。

### 正式 spec 的目标与内容（已确认）

用户确认：spec 应成为功能或需求的长期行为真相源，让不了解讨论过程的人能够理解、实现、验证和演进该功能。

建议覆盖范围包括（按需使用，不是固定十四段模板）：

- 目标与问题；
- 范围与边界；
- 必需的术语和概念；
- 参与者与权威所有者；
- 正常功能行为；
- 状态、事件和生命周期；
- 逻辑接口与集成契约；
- 数据、身份、持久化和缓存；
- 失败与恢复；
- 时间、并发和多客户端；
- UI 或消费者的可观察行为；
- 当前实现映射，或全新功能的现有系统约束；
- 现状偏差与演进方向；
- 可验证的验收标准。

这些内容按实际领域边界使用，不构成固定模板。正式 spec 默认不包含任务拆分、负责人、排期和实现步骤。

## 已确认的 Grilling 修改

目标文件：`skills/mattpocock-productivity/grilling/SKILL.md`

现有文件很短，当前强制一次只问一个问题且不维护文件。用户确认需要做以下增强：

### 批量提问

- 按同一主题和依赖关系组织一批问题，而非固定一次一个。
- 每项提供 Agent 推荐方案和理由。
- 代码或文档能回答的事实不要询问用户。
- 用户未回答的项不得默认为同意。

### 批次状态纪律

这是用户特别强调的规则：

- 当前批次没有全部解决前，不得提出下一批问题。
- 用户只回答部分问题时，只处理当前批次剩余项。
- 解释中发现的新分支归入当前批次补充，不开启下一批。
- “继续”不代表当前批次已经确认。
- 回答当前批次疑问时，结尾不得顺带提出下一批。
- 当前批次所有问题都得到明确答案后，Agent 可以自行宣布批次关闭并直接进入下一批，不需要再要求用户确认一次。
- 如果用户明确要求暂停或转换主题，即使当前批次已关闭也不得开始下一批。

### 可选决策记录

- 调用方提供记录路径时，Grilling 必须维护该记录。
- 用户要求记录但没有给路径时，默认 `.scratch/<topic>-decisions.md`。
- 普通 Grilling 没有记录要求时，不强制创建文件。
- `write-spec` 使用 Grilling 时始终启用决策记录。
- `write-spec` 负责确定主题和路径；Grilling 负责创建或继续维护文件。
- 已存在记录时，修改前必须重新完整读取，保留用户修改。
- 不自动删除最终决策记录。

决策记录不能只写最终答案，还应保留：

- 问题背景；
- 相关代码或文档事实；
- 待决定的分支；
- Agent 推荐及其原因；
- 用户决定及用户明确提供的原因；
- 对旧决定的覆盖和影响；
- 待确认或已确认状态。

不得替用户编造没有表达过的理由。Agent 推荐理由和用户理由必须分开。

### 已确认的 workflow 与停止条件

采用以下阶段：

```text
定位与范围
→ 事实调查
→ 行为与领域边界建模
→ 分批决策
→ 一致性审计
→ 用户授权
→ 正式成稿
→ 成稿验证与修订
```

- 简单需求可以合并或压缩阶段，但不能省略事实调查、必要决策、用户授权和成稿验证。
- 讨论闭合要求：所有会影响规范行为、领域边界或演进方向的决定都已明确确认。
- 不影响规范的未解决事实可以标为已知未知项，但不得伪装成确定结论。
- 仍存在阻塞性规范决策时，不得请求成稿授权。
- 只有“写 spec”“开始成稿”“可以实施 skill”等明确表达才算授权。
- “继续”“没问题”“按推荐来”只关闭当前决策，不自动授权写文件。

### 已确认的 `write-spec` 与 Grilling 组合方式
