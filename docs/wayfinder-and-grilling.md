# Wayfinder 与 Grilling：如何选择与配合

`wayfinder` 和 `grilling` 都用于在实施前消除不确定性，但它们解决的是不同层级的问题：

> `grilling` 是一次深入访谈；`wayfinder` 是管理多轮探索过程的地图。

它们不是互相替代的两个流程。Wayfinder 会把复杂探索拆成不同类型的 ticket，其中的决策型 ticket 通常正是通过 Grilling 解决。

## 核心区别

| 维度 | Grilling | Wayfinder |
| --- | --- | --- |
| 解决的问题 | 一个方案里还有哪些地方没想清楚？ | 一个庞大、模糊的目标需要经过哪些探索才能变清楚？ |
| 适用规模 | 通常一次连续会话可以覆盖 | 明确针对跨越多次会话的大型工作 |
| 工作方式 | 沿决策树逐层追问，一次只问一个问题 | 建立 Map 和子 tickets，每次会话解决一个 ticket |
| 主要产物 | 用户和 Agent 对方案达成共同理解 | 可持续、可协作、带依赖关系的决策地图 |
| 状态保存 | 主要存在于当前对话；包装 skill 可以额外写文档 | 保存在 GitHub、GitLab 或本地 Markdown issue tracker |
| 调研与原型 | 不是主要职责 | 可以组合 research、prototype、grilling 和 task |
| 完成条件 | 当前方案的关键分支已经讨论清楚 | 通往目标的关键未知已经消除，可以编写规格 |

## 什么时候使用 Grilling

当你已经有一个相对具体的方案，但担心其中还有遗漏、错误假设或未确定的边界时，使用 Grilling。

典型场景包括：

- 已决定使用 PostgreSQL，想讨论租户隔离方案；
- 已有登录系统设计，想检查异常流程；
- 已经写出一版 API，希望压力测试接口设计；
- 准备开发某个功能，但权限、错误处理或边界条件还没确定；
- 整个问题可以在一次连续讨论中掌握。

Grilling 沿着一棵“决策树”工作。它一次只问一个问题，等待用户回答后，再根据答案选择下一个问题。每个问题还应附带 Agent 的推荐答案。

例如：

> 普通成员能否看见团队中其他成员创建的草稿？
>
> 我的建议是默认不可见，发布后才对团队可见。你是否同意？

如果某个事实可以通过检查代码库得到，例如项目当前使用什么数据库，Agent 应该自行检查，而不是询问用户。真正需要用户决定的问题，才进入访谈。

## 什么时候使用 Wayfinder

当目标很大、路线模糊，甚至无法一次性说清楚“需要讨论哪些问题”时，使用 Wayfinder。

典型场景包括：

- 从零建设一个新产品；
- 设计规模很大的功能或系统；
- 对大型系统进行多租户改造；
- 规划涉及数据、权限、计费和基础设施的迁移；
- 工作明显超过一次 Agent 会话；
- 后续问题依赖前面的答案，现在还无法完整拆分；
- 需要多人或多个 Agent 会话共享探索进度。

Wayfinder 首先确定 Destination，即探索结束时应该获得什么。然后在 issue tracker 上建立一张 Map，将当前能描述清楚的问题建立为子 tickets，并记录：

- **Decisions so far**：已经解决的问题；
- **Not yet specified**：知道存在，但目前还无法准确描述的问题；
- **Out of scope**：明确排除在本次目标之外的内容；
- ticket 之间的阻塞关系；
- 当前可执行、未被认领的 frontier。

Wayfinder 中的 ticket 分为：

- **research**：调查文档、第三方 API 或外部知识；
- **prototype**：制作低成本原型，让用户对具体行为作出判断；
- **grilling**：通过一问一答解决决策；
- **task**：完成阻塞后续决策的准备工作。

因此，Wayfinder 是探索过程的编排层，Grilling 是它解决具体决策的一种手段：

```text
Wayfinder：管理整个探索过程
    │
    ├── Research：查清外部事实
    ├── Prototype：做出具体事物供人判断
    ├── Task：完成阻塞决策的准备工作
    └── Grilling：通过对话作出具体决策
```

## Wayfinder 之后还需要 Grilling 吗

需要区分“创建完 Map”与“完成整张 Map”。

### 创建完 Map 之后

通常仍然需要 Grilling。

创建地图只是识别出目前能够看清的问题，并将它们组织成 tickets。例如：

- 确定目标用户——`grilling`；
- 调研数据合规要求——`research`；
- 验证人工接管交互——`prototype`。

后续处理“确定目标用户”时，就会运行一次 Grilling，通过实时问答解决这个决定。

### 整张 Map 完成之后

原则上不再需要一次大规模 Grilling。

Wayfinder 的完成条件是：开始编写规格或实施之前，已经没有重要问题必须先决定。

不过，在整理规格时仍可能发现遗漏：

- 如果只是局部小问题，可以临时使用 Grilling 补齐；
- 如果出现大片新的未知，通常说明 Wayfinder 结束得太早，或者项目目标发生了变化，应重新进入 Wayfinder。

完成 Wayfinder 并不意味着以后不能再使用 Grilling，而是意味着不应该还剩下大量依赖 Grilling 才能解决的核心问题。

## 为什么 Wayfinder 之后还需要 to-spec 和 to-tickets

Wayfinder 的 tickets 是“探索与决策 tickets”，而 `to-tickets` 产生的是“开发与交付 tickets”。两者名字相同，目的却不同。

| Wayfinder tickets | `to-tickets` 产生的 tickets |
| --- | --- |
| 回答“应该做什么、为什么” | 说明“具体怎么把它做出来” |
| 关闭意味着一个未知已经消除 | 关闭意味着一部分产品已经实现 |
| 产物是决策、研究报告或原型 | 产物是代码、测试、迁移或部署 |
| 随着认知逐渐展开 | 从相对稳定的规格中拆分 |

### to-spec 的作用

Wayfinder Map 是探索历史和决策索引，不是一份完整、连贯、可验收的产品规格。

`to-spec` 将分散在不同 tickets 中的决定整理成统一规格，例如：

- 用户与使用场景；
- 功能行为；
- 数据模型；
- 权限规则；
- 异常流程；
- 非功能要求；
- 验收标准；
- 明确不做的内容。

Wayfinder 证明路线已经想清楚；Spec 描述最终要建设的东西。

### to-tickets 的作用

`to-tickets` 再把稳定规格拆成可以开发、测试和交付的实施任务。探索 tickets 不应该直接充当开发任务，否则容易将“做决定”和“做产品”混在一起。

完整流程是：

```text
Wayfinder
发现并解决“我们还不知道什么”
    │
    │ 内部可能多次使用 Grilling
    ▼
to-spec
把已经确定的答案组织成完整规格
    ▼
to-tickets
把规格拆成可实施、可验收的开发任务
    ▼
implement
完成交付
```

如果项目很小，Wayfinder 最终得到的决定可能已经足够直接实施，可以跳过部分步骤。但对于真正大到需要 Wayfinder 的项目，探索 tickets 和开发 tickets 通常应该分开。

## 示例：建设企业 AI 客服平台

假设目标是建设一个接入网站、微信和邮件的企业 AI 客服平台。

### 情况一：直接使用 Grilling

团队已经确定：

- 第一版服务公司内部客服团队；
- 使用现有大模型 API；
- 数据存储在 PostgreSQL；
- AI 无法回答时转人工；
- 首期只接入网站聊天窗口；
- 两个月内上线 MVP。

现在主要不确定的是“AI 转人工”的具体行为。这个问题范围明确，可以直接使用 Grilling，逐个讨论：

1. 什么条件触发转人工？
2. 转人工后，AI 是否继续生成建议回复？
3. 没有客服在线时如何处理？
4. 用户能否主动要求人工？
5. 人工接管后，AI 是否能重新取得控制？
6. 哪些转人工原因需要进入质量分析？

最后形成共同理解：

- 用户主动要求人工时立即转接；
- 连续两次低置信度回答后自动转接；
- 没有客服在线时创建异步工单；
- 人工接管后，AI 只生成内部建议，不直接发送；
- 每次转人工必须记录结构化原因。

问题已经足够清楚，可以进入规格或实施，不需要为它建立 Wayfinder Map。

### 情况二：使用 Wayfinder

团队目前只有一句：

> 我们想做一个企业 AI 客服平台，但产品形态、技术路线和商业模式都还没确定。

此时存在大量相互依赖的未知：

- 面向内部团队还是对外销售？
- 服务中小企业还是大型企业？
- 产品是聊天机器人、客服工作台，还是二者都有？
- 如何接入企业知识？
- 如何处理权限与敏感数据？
- 支持哪些渠道？
- 人工接管如何工作？
- 怎样评估回答质量？
- 按席位、消息量还是模型消耗收费？
- 是否允许客户选择模型供应商？
- 是否需要满足数据驻留要求？

Wayfinder 可以将 Destination 定义为：

> 形成一份能够交给产品和工程团队编写 MVP 规格的完整决策集，明确目标客户、产品边界、交互模型、技术约束和成功指标。

第一批探索 tickets 可能是：

- `[grilling]` 确定第一版目标客户；
- `[research]` 调查目标行业的数据合规要求；
- `[prototype]` 制作“AI 自动回复与人工接管”的交互原型；
- `[grilling]` 确定 MVP 的渠道范围；
- `[research]` 比较知识库检索方案。

这些 tickets 还存在依赖关系：

```text
确定目标客户
   ├──→ 调查合规要求
   ├──→ 决定多租户隔离级别
   └──→ 确定定价单位

确定客服工作流
   └──→ 制作人工接管原型
          └──→ 决定会话状态模型
```

执行“确定第一版目标客户”时，Wayfinder 会使用 Grilling：

> 第一版应该优先服务内部客服团队，还是作为 SaaS 销售给其他企业？
>
> 我的建议是先服务内部团队，因为这样可以更快获得真实对话数据，也暂时不需要处理完整的多租户计费。你怎么看？

这个决定完成后，Wayfinder 会：

- 把答案记录为 ticket 的 resolution；
- 关闭该 ticket；
- 在 Map 的 Decisions so far 中增加一行摘要；
- 根据答案更新或创建新的 tickets；
- 让后续会话继续处理 frontier 上的问题。

假设探索结束后得到以下决定：

- 目标用户是 50～500 人的电商客服团队；
- 第一版只支持网页聊天；
- 使用共享数据库和 `tenant_id` 行级隔离；
- 人工接管后，AI 只生成内部建议；
- 使用解决率、转人工率和人工纠正率衡量质量。

`to-spec` 会把这些分散的决定整理成连贯规则：

> 当用户主动要求人工，或连续两次回答低于置信度阈值时，系统将会话转入 `waiting_for_agent` 状态。
>
> 客服接管后，AI 不再直接向用户发送消息，但继续为客服生成建议回复。
>
> 没有客服在线时，系统创建异步工单并告知预计响应时间。

随后，`to-tickets` 将规格拆成实施任务：

- 创建会话状态机；
- 实现置信度转接规则；
- 实现客服接管 API；
- 实现异步工单创建逻辑；
- 实现 AI 建议回复；
- 添加状态转换集成测试。

## 选择口诀

> 能说清楚“我要讨论哪个方案”，使用 Grilling。
>
> 只能说清楚“我要去哪里”，但还不知道沿途要解决什么，使用 Wayfinder。
