# Write Plan

## 目的

把会话中的目标写成 implementation plan。

implementation plan 必须让未参与前期讨论的人能理解要做什么、为什么做、准备怎么做，以及需要完成哪些任务。

只生成 plan，不开始实施。

## 必答问题

### 1. 目标是什么？

说明要达成的结果、适用范围和明确的非目标。优先描述可观察的结果，不要把实施手段写成目标。

### 2. 为什么有这个目标？

说明触发目标的问题、背景或机会，以及它的价值。区分已知事实与推断，不编造动机。

### 3. 方案是什么，为什么选它？

说明被选方案、关键机制、适用边界和主要取舍。如果存在具有实质差异的备选方案，说明为什么选择当前方案；不要为了形式完整虚构备选方案。

### 4. 如何拆分任务？

把方案转换为任务清单，并遵守以下规则：

1. 简单工作可以只有一个任务，不为拆分而拆分。
2. 每个任务只包含一个逻辑变更。缺陷修复与性能优化、API 变更与使用该 API 的功能，应分别拆分。
3. 一个逻辑变更即使涉及多个文件，也应保持为一个任务；不按文件、目录或技术层机械拆分。
4. 每个任务都应容易理解、可以验证，并有单独成立的理由。
5. 任务可以依赖前序任务，但应明确依赖关系并按依赖顺序排列。
6. 完成任一任务后，项目都应能正确构建和运行，不留下需要后续任务修复的破损状态。
7. 拆分任务不考虑 TDD。除非目标明确要求测试，否则是否编写测试由任务执行者决定。

这些规则约束 plan 中的任务拆分，不约束任务执行者如何组织 Git commits。

## 输出结构

根据实际内容调整小节，但保留以下四个一级部分：

```markdown
# <Plan 标题>

## 目标

<目标、范围、非目标>

## 背景与动机

<问题或机会、为什么现在需要做>

## 方案

<选定方案、关键机制、选择理由与取舍>

## 任务拆分

<按任务拆分规则组织的任务清单>
```

## 注意事项

- 保持目标、方案和任务之间的可追溯性：方案服务于目标，任务服务于方案。
- 保留对理解决策有用的上下文，删除不影响执行的讨论过程。
