# Write Spec

## 目的

把新功能、或既有功能补建需求，收敛成一份或多份长期可维护的正式 spec，使不了解原始讨论的人也能理解、实现、验证和演进该功能。

正式 spec 是规范行为、领域边界、集成契约和可验证结果的长期真相源。它记录最终一致结论，不保存完整讨论历史，也不充当 implementation plan。

## 术语

- **核心问题**：正式 spec 必须回答的问题，用于定义文档内容，不是直接向用户提出的一组访谈问题。
- **覆盖模型**：核心问题与已确认事实、未知事实、决策分支及最终答案之间的工作映射，不是正式 spec 的固定结构。
- **决策分支**：为回答核心问题而需要用户作出选择的具体事项。
- **frontier**：Grilling 中所有前置分支都已收敛、当前可以讨论的决策分支。
- **讨论回合**：Grilling 围绕当前 frontier 发起并等待用户回应的一轮讨论。
- **收敛**：用户已经明确选择或确认某个决策分支的结论。

## 产出

产出一份或多份能够回答本 skill 所列核心问题的正式 spec。章节标题和组合方式由领域决定；一个章节应主要回答一个核心问题，必须结合才能完整表达行为的核心问题可以合并，不适用的核心问题不制造空章节。

把事实、讨论来源、备选方案、推荐及理由、用户决定和覆盖关系保存在 decision log 中，默认不提交，默认路径为 `.scratch/<topic>-decisions.md`。

按以下优先级确定正式 spec 的路径：

1. 用户明确指定的路径；
2. repository-local instructions；
3. repository 根目录下的 `specs/`。

把 `AGENTS.md`、`CLAUDE.md`、`CONTEXT.md` 等文件声明的位置视为 repository-local instructions；即使目标目录尚未创建也必须遵循。只有 repository 没有相关约定时，才 fallback 到 `specs/`。

## 何时拆成多份 spec

一份 spec 应具有清晰且单一的权威范围。当内容具有不同的领域边界、权威所有者、消费者群体或独立演进节奏时，拆成多份 spec。不要仅因文档较长而拆分。

消费者或触发者拥有复杂且相对独立的规则与交互场景时，可以建立独立 spec。核心 spec 仍保留参与者清单、它们与状态模型的关系、共享规则和摘要；独立 spec 完整拥有其详细规则与场景。

多份 spec 必须互相引用，并分别声明自己权威回答哪些核心问题、只引用而不拥有哪些核心问题。不要在多份文档中重复维护同一规则。

## 核心问题

### 这份 spec 规范什么？

说明目标、范围、非目标、相邻领域边界，以及这份文档对哪些行为和规则具有权威性。

### 系统有哪些规范状态，每个状态意味着什么？

说明适用的状态、状态语义、不变量和权威所有者，并定义准确理解它们所需的术语、参与者与身份。若功能没有实质状态模型，不要人为制造状态；改为说明其规范输入、输出和行为不变量。

### 什么会触发状态转换，转换遵循什么规则？

说明触发事件、转换成立与不成立的条件、转换前后的状态，以及各方能够观察到的结果。若某个特殊条件会改变转换或其结果，在对应规则中一并说明；不要为与当前功能无关的场景制造规则。

若功能没有实质状态模型，回答：在什么条件下，系统必须产生什么规范行为和可观察结果？

### 谁触发和消费这些状态及转换，各自能依赖什么？

说明触发者、消费者、它们与状态模型的关系，以及各方必须遵守或可以依赖的业务规则、集成契约和 UI 可观察行为。

### 目标模型与当前系统有什么关系？

对于已有实现，始终区分目标模型、当前实现映射和现状偏差。当前实现与目标模型冲突时，以目标模型表达演进方向，同时如实记录偏差，不把偶然实现固化成目标规则。

对于全新功能，说明现有系统约束、相邻边界和集成条件，不编造尚不存在的当前行为。

### 如何证明实现符合规范并可以安全演进？

分别说明：

- 已有保障：当前有哪些测试、约束或可观察证据保障相关行为；
- 演进验收：达到哪些可观察、可验证的结果，才说明实现符合目标模型。

## 可采用的手段

1. 阅读相关代码、测试、已有 spec、领域文档、配置、ADR 和 repository 历史，建立事实与约束的证据基础。能从 repository 中查明的事实不要询问用户。

2. 若规范依赖 repository 外的协议、第三方 API 或当前版本行为，查阅对应 primary sources。外部资料只提供事实证据，不能替用户决定产品行为。

3. 根据适用的核心问题建立覆盖模型，整理已确认事实、尚未确认的事实、需要用户选择的决策分支，以及不阻塞规范的已知未知项。不得把推断写成用户决定。

4. 加载 `/grilling`，使用它完成全部决策讨论并维护 decision log。向它提供 topic、decision log 路径、已调查事实、未解决的决策分支和推荐方案；明确排除已确定事实，以及文档位置、格式等编辑性选择。

5. 使用具体场景检验候选规则：给定参与者、前置状态和触发事件，推演转换是否发生、转换后的状态以及各方能够观察到的结果。只检查与当前领域实际相关的场景。

## 回合收敛纪律

决策分支只有在用户给出明确选择或确认总结后才算收敛。当前回合只有在其所有决策分支都已收敛后才算结束。用户只回答了部分分支，或者仍在补充思考、提出异议、追问、附加条件、评价推荐时，继续处理当前回合；这些反馈不自动代表相关分支已经确认。

在当前回合结束前，只回应和收敛本回合的决策分支。不要一边回应上一轮尚未解决的反馈，一边重算 frontier 或引入下一回合才能讨论的新分支。

不要把已由用户指令、repository-local instructions 或已确认事实决定的内容重新包装成决策分支。

## 成稿前一致性审查

完成讨论后、写正式 spec 前，分发一个 fresh-context、read-only subagent，要求它回答：

- 后来的决定是否明确覆盖并修正旧决定？
- 术语、状态、事件、契约和消费者行为是否彼此一致？
- 各项决定对同一状态、事件或场景规定的前置条件、转换结果和可观察结果是否一致，是否存在未定义或互相冲突的行为？
- 目标模型、当前实现映射、现状偏差、已有保障和演进验收是否被混淆？
- 每个适用的核心问题是否已有完整答案，每项规范行为是否具有可观察、可验证的结果？

若审查发现新的决策分支，返回 Grilling 继续讨论，不得自行补答案。只有所有会影响规范行为、领域边界或演进方向的决定都已确认，才可宣布 shared understanding 已达到。不影响规范的未知事实可以作为明确的已知未知项保留；阻塞性问题不得带入正式 spec。

shared understanding 达到后，向用户说明预定生成的 spec 及路径、各自的权威范围和仍保留的非阻塞未知项，并明确请求成稿授权。

## 成稿后验证

完成正式 spec 后，启动一个新的 fresh-context、read-only subagent，要求它回答：

- 是否遗漏已确认决定，或把未确认内容写成规范？
- 被覆盖的旧决定是否仍有残留？
- 跨文档术语、引用和权威边界是否一致？
- 每个适用的核心问题是否得到清晰回答，验收结果是否足以验证目标行为？
- 文档是否无意锁死实现，或混入 implementation plan？

若验证发现新的语义决定，停止成稿，返回 Grilling，并在重新收敛和审查后再次取得写入授权。最终报告生成或修改的 spec 路径。

## 注意事项

- 除非实现细节本身已经成为必须保留的约束，否则不要固定类名、函数名、存储机制、HTTP 路径、算法或实施步骤。
- 当前实现映射可以引用稳定的模块路径和 symbol，但不要依赖容易漂移的行号。
